Where the build stands

A working turf-booking product shipped in two days: players book and pay a flat ₹150 advance for each hour (recorded, not yet collected), then pay the rest at the venue. The next gates are quality (no tests, no CI), security (identity and wallet), and storage scale, all before online payments.

First target: 1,000 users

What has to be true before you invite them

  1. Move off Vercel Hobby. It forbids commercial use. Use Vercel Pro ($20 a month) once owners and players are real.
  2. Move the database to Supabase Pro ($25 a month). Free projects pause after 7 days idle; two of your other projects already show as paused.
  3. Run supabase/setup/5-delta-sync.sql on production (task P10-13). The code now syncs only changed rows instead of the whole database per request; the SQL step switches it on. See the Cost & scale tab.
  4. Add tests and CI for pricing and double-booking (P8-02, P8-04, P8-08).
  1. Close the money and identity risks: rotate the old Supabase key, bind wallet to the signed-in account, shared rate limiting (P9-01, 03, 06).
  2. Backups and monitoring: nightly dump, Sentry, uptime check on /api/health.
  3. Paper: partner agreement, refund and commission policy, privacy review, a custom domain.
  4. The ₹150 an hour advance is only recorded. No money is taken until Razorpay is added (phase 11). Decide whether the pilot collects it by UPI by hand, or waits. Until then, do not describe it to players as paid.

Progress by phase

Three biggest gaps

  1. No tests and no CI. Pricing, cancellation and the double-booking guard have no automated check. A change to src/lib/pricing.ts ships unverified.
  2. No online payment and no messages. Players can't pay or leave a deposit, and nobody gets a confirmation or reminder. No-shows cost owners, and commission is 0.
  3. Player identity is weak. Without Clerk it is a localStorage name and phone. Wallet spend is keyed by a typed phone number, and a ticket link exposes name and phone to anyone holding it.

What works today

  • Browse 10 launch turfs, filter by area and sport, live hourly slots for the next 7 days, full or half pitch where the turf splits.
  • 8-minute slot holds per device, up to 6 slots per booking, promo, referral and add-ons, server-side quote.
  • Booking with a flat ₹150 advance per hour (10% of the hour's price, never under or over ₹150, so 3 hours is ₹450), the rest paid at the venue; ticket with QR, invoice, calendar file, self-cancel until 2 hours before.
  • Reviews after check-in, saved turfs, WhatsApp share.
  • Owner dashboard (pricing rules, offers, blocks, check-in desk, payouts CSV, staff roles) and admin console.

What does not exist

  • Real money movement: the advance is recorded as paid but nothing is charged. Razorpay is planned for phase 11.
  • Any outbound message: no SMS, WhatsApp, email or push. Only the error webhook.
  • Tests, CI, staging, backups policy, uptime monitor.
  • Find players, tournaments, weather alerts, real map, admin analytics.

Architecture

A modular monolith: one Next.js 16 app on Vercel, one Supabase Postgres used as a document store behind the service-role key. The browser never talks to the database.

Module map

src/app/(main)
public site, arenas, tickets, profile, saved, list-turf, FAQ, legal
src/app/(auth)
Clerk sign-in/up or device-form fallback
src/app/partner
owner dashboard, permission-gated pages, payouts CSV
src/app/admin
approvals, turfs, partners, players, refunds, settings
src/app/api
health, holds/release, client-error
src/lib
domain: store, pricing, wallet, reports, reviews, session, rate-limit, realtime
src/utils/supabase
admin (secret key), browser, server, middleware helpers
src/components
shell, turf cards, consent, dash UI kit, invoice

Conventions worth knowing

  • Next 16 style: proxy.ts not middleware, async params, connection(), after().
  • Styling is CSS Modules plus tokens in globals.css. No Tailwind, no UI library.
  • No client state library. Server state per request through getDb(); mutations are server actions plus revalidatePath('/', 'layout').
  • Device state (profile, favourites, booking ids) in localStorage, synced by DOM events.
  • Prices come from one function used for both the quote and the charge, so they cannot drift.
  • Times are IST helpers in lib/time.ts.

              STRIDE by element

              DREAD = Damage, Reproducibility, Exploitability, Affected users, Discoverability, each 1 to 10. Anything at 6 or above needs a named owner before the next release.

              Ship gate

              Eight-category pre-launch audit, answered from the code. A check marked MANUAL needs a person to confirm it; SKIP does not apply to this stack.

              Tech debt and scale

              Ordered by what hurts first as traffic and team size grow.

              Target direction for storage

              Keep the jsonb tables for low-churn config (turfs, partners, pricing) and move the hot path to scoped reads and per-row locking.

              1. Stop downloading every table per request. Done with delta sync (load_changes); next, keep old bookings out of the in-memory copy so cold starts stay small.
              2. Replace the global rev with a version per turf (or per slot) so two turfs never conflict.
              3. Promote bookings, holds and wallet transactions to typed columns with CHECK constraints and foreign keys.
              4. Cache public pages (ISR plus tag revalidation on writes) so browsing never touches the store.
